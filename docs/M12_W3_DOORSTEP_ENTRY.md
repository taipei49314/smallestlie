# W3 entry and readiness boundary

The new single-action receiver is outside the frozen Phase-1 asset closure.
It authenticates the EC runtime before importing it, obtains fresh native
source evidence through a mutually bound tokenless pipe, re-prepares the exact
approved request, checks the original lock/ticket/prefix, then calls the unchanged
frozen collector once. The parent keeps custody of the original inputs, complete
code and installed-image maps until native writer and stream closure.

The `m12-w3-doorstep-qualify` declaration names a new bounded readiness route.
The ordinary executor must not run its product guard directly: the reviewed EC
workflow imports its trusted qualification harness, retaining the actual new job
identity for the App check and immutable receipt. The parent alone owns the
read-only GitHub credential. Native toy children have no credential, and synthetic
session identities cannot become the formal `checkwash-wave-3` session.

The authorization is the human instruction “授權直接到w3門口 再由我審核是否啟動w3”.
It permits implementation, bounded HOST50 qualification and ordinary delegated
delivery. It does not permit formal initialization, release of a W3 ticket,
execution of its fixtures or verifier, or a formal dispatch series. The final
review must bind the qualified source, actual evidence, limits and responsibility
references before a separate direct-human startup decision is imported.

Phase-1 commit, manifest, classifications, detectable twins, 208 frozen assets,
collector and engine pin remain unchanged. A detectable twin retains the same
effective cheating in a nearby shape that the engine catches; honest and repaired
tests remain separate controls.
